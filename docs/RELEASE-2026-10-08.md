# 2026-10-08の監視と定期復元検査

ユーザーの着手指示に基づき、司令塔・実装者・レビュワーで、監視の実行間隔とバックアップの定期復元検査を進めた。本番反映の確認結果は末尾へ追記する。

## 変更

- `tossa-operations-monitor` を別Workerとして配置する。公開HTTP経路・D1 bindingを持たず、5分Cronでヘルス・4Queue・26時間以内のv2保存実績・8日以内の復元検査証跡を観測する。監視の開始・完了時刻を専用KVへ保存する。
- メールは確認済み管理者の宛先Secretとnative EMAIL bindingを使い、同じ異常を30分抑制、正常復帰を通知する。全宛先のAPI受理後に状態を進め、失敗と試行モードでは次回再試行する。KVの結果整合による重複可能性はある。
- GitHubは毎時23分の補助監視へ変更。ヘルス・Queueに加え、完了から15分超のheartbeatを異常とする。15分は判定条件で、毎時実行とschedule遅延を含む検出期限ではない。前の5分設定で約5時間の空きを確認したが、原因は未確定。
- 毎週月曜13:17 JSTに最新の非公開v2バックアップをlocal D1へ復元し、17表の全行値・件数・外部キー・quick_checkを照合する。許可項目だけの証跡をR2へ一意キーで保存し、読み戻してSHA-256を照合する。本番D1の問い合わせ・export・復元を行わず、元JSON・SQL・DBは非公開一時領域から削除する。
- GitHub `production` Environmentの許可ブランチをmainだけに制限する。手動workflowの別ブランチから本番Secretsを利用できる設定を閉じる。

## 検証で修正した点

初回の実行で、R2一覧へprefixを渡し忘れ `undefined` を検索していたことと、remote CLI向けの環境変数整形で子の復元runnerに必要なaccount IDを落としていたことを発見した。失敗は静的コードで私有R2へ記録し、原文や認証情報は公開しなかった。prefixと子プロセスの環境変数に回帰検査を追加した。

Workerはバックアップの元キー時刻で鮮度を判定し、metadataがあれば一致を必須とする。再アップロードの保存時刻だけで古いアーカイブを新しく扱わない。NodeとWorkerは共通の厳格な復元証跡validatorを使用する。

実Cronの初回にHTTP検査だけが即時失敗し、local Wrangler/workerdで `redirect:'error'` がedgeで未実装の例外になることを再現した。`manual`へ変更し、3xxを追跡せず異常として扱う。修正後は同じランタイムでhealth 200を確認し、6件のfetch設定に回帰検査を追加した。Cron自体はUTC 23:22と23:27の実行を確認し、修正前もR2の保存・復元証跡検査は成功している。

KVの同一キー1秒1書込制限を踏まえ、開始ログと完了時一回のheartbeat保存に整理した。中断時は古い完了時刻または欠損として検出し、開始だけで稼働正常と扱わない。

実アカウントのQueue一覧には別プロジェクトの3キューも含まれるため、それらを除外してtossaの4キューに検査を限定した。対象キューの欠落・重複・不正IDとレスポンス不正は異常として維持し、実際の7キュー構成を回帰検査に追加した。

Queue APIの実成功応答は `success:true, errors:null` だった。エラー配列だけを許す検証が成功を拒否していたため、nullも無エラーとして受け付ける。非空エラー配列や不正形式は引き続き失敗扱いにする。HTTP状態・通信・JSON・API形式の診断は固定コードだけで、応答本文を記録しない。

## 実バックアップでの確認

2026-10-08 08:26 JSTに自動選択した最新アーカイブ（前日12:00 JST取得開始、35,472バイト）を隔離local D1へ復元した。17表・124件の件数と全行値、外部キー、quick_checkが一致。成功証跡を非公開R2へ保存し、読み戻して完全一致とSHA-256を確認した。[非機密の結果](benchmarks/2026-10-08-scheduled-recovery.json)。取得2.646秒、復元・照合110.996秒、全体124.741秒。これは端末上の小規模実測で、復旧時間の保証ではない。

GitHub production Environmentは `custom_branch_policies:true`、許可パターンは `main` のbranchだけであることをAPIで確認した。

最終修正版の2026-10-08 10:37 JST Cronは `healthy`、4観測が全て `ok`、異常コードなしだった。通知は不要で送信していない。これを確認して `OPERATIONAL_ALERT_DRY_RUN=false` へ切り替える。初回CI `37713273763` はnull応答の修正前の版を配信しないよう意図的に取り消し、最終版で全体検査を再実行する。

## 運用上の制約

送信ドメインの状態と受信箱への実着信は未検証。GitHubのメール専用tokenも未設定で、補助監視の異常は失敗runとして確認する。Cloudflare全体・アカウント障害では一次監視とEmailも影響を受けうる。独立したメール基盤は今回追加しない。

既存のCI用Cloudflare tokenを使用し、監視に必要な読み取り権限だけの専用tokenへ分離する作業は残る。週次検査の最大100MiB、一表32MiBの比較上限、日次JSONの200ページ上限は維持する。小規模の復元成功から本番規模の復旧時間を保証しない。広域・持続負荷、実機の項目別記録、地域試用、tsudoiの実フィード接続は別の残課題。
