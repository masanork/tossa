# tossa.app の規模と負荷測定

2026-10-06更新。現行は Cloudflare Workers Paid、D1 1本、KV、R2、Queues。**本番の同時利用者数や毎秒書き込みの限界は未測定**。以前の「同時数千〜数万」「秒間10〜20件」などの数字には負荷試験の裏付けがなく、容量の根拠として使わない。投稿件数だけでDB移行や費用を判断しない。

[D1の制約](https://developers.cloudflare.com/d1/platform/limits/)ではPaidのDB容量は10GB、1つのprimaryはクエリを直列に処理する。処理能力は件数よりSQLの時間・行読み・読み書きの混在に左右される。1万投稿をD1の上限とは扱わない。

## 今回追加した対策

- **公開フィード更新を直列化**: 書込Queueのconsumer並列数を1に制限し、書き込み後・管理画面・CronからのKV更新を同じconsumerへ集約する。1バッチ内の更新要求は一つの公開処理へまとめ、KV保存失敗は更新ジョブだけを5秒後に再試行する。コミット済み投稿を公開失敗だけで書き直さない。直近のスナップショットで更新を省略した場合も、3秒後の更新ジョブを残す。
- **平常時の一覧を新鮮に保つ**: 毎分Cronで公開スナップショット更新を要求する。KV生成後120秒以内のスナップショットを採用し、時刻が未来の場合は採用しない。静かな時間にも旧10分Cronを待つことでD1へ閲覧が集中していた経路を改善した。公開GETからは本番の更新ジョブを作らず、冷えたキャッシュへの閲覧数に比例して書込Queueを埋めない。検索・範囲・近傍・自分の投稿・明示更新はD1を使う。
- **一斉Pushを100件ずつ展開**: リクエストでは対象の上限IDと通知ジョブのみを受け付ける。Queue側で対象をID順に最大100件読み、配信ジョブと続きのページを投入する。地域・通知種別・除外ユーザーの判定はSQLで行う。従来の配信ジョブも引き続き処理できる。画面は受付と送信完了を区別する。
- **測定と観測**: `npm run load:local` とCIの小規模な負荷検査を追加。Workers observabilityを有効にし、実行ログを10%サンプリングする。「規模」画面は件数と鮮度を示し、同時利用者数や追加費用なしの運用を保証しない。

[KVは結果整合](https://developers.cloudflare.com/kv/concepts/how-kv-works/)で、地域間で反映に60秒以上かかりうる。上記120秒はサーバーがスナップショットを採用する条件で、画面の反映期限の保証ではない。別に15秒の公開キャッシュと`stale-while-revalidate=60`がある。緊急の現地確認や自分の書き込み直後の確認には明示更新を使う。同一キーの[KV書き込み上限](https://developers.cloudflare.com/kv/platform/limits/)やQueue滞留で更新に失敗・遅延する場合はD1へフォールバックする。

[consumer並列数の制限](https://developers.cloudflare.com/queues/configuration/consumer-concurrency/)はDB負荷を抑える一方、処理量を超える入力を受け続ければ滞留が増える。Queueを無限の容量として扱わず、最古メッセージの待ち時間・DLQ・受領から反映までの時間を監視する。一斉Pushのページ再配送では同じ通知タグを再利用するが、送信ジョブ自体が重複する場合はある。配信が一度だけになる保証ではない。上限IDは探索を有限にするための境界で、対象者全員を受付時点の完全なスナップショットとして固定するものではない。

## ローカル負荷測定

```sh
npm run load:local -- --sizes=5000,20000,50000 --requests=120 --concurrency=12 --output=/tmp/tossa-local-load.json
```

隔離した一時ディレクトリのworkerd・SQLite・KVで合成投稿を作り、実際のHTTP APIを測る。本番の接続先、認証情報、投稿、通知送信は使わない。接続先を外部URLへ変更するオプションはない。7経路を各120リクエスト、並列12で測り、HTTP状態・エラー数・データ取得元・p50/p95・最大時間をJSONへ記録する。キャッシュ温存の公開一覧と、キャッシュを明示的に避けるD1一覧・文字検索・タグ・bbox・近傍・深いページを分ける。CIでは5千投稿・各30リクエスト・並列4で経路と応答を検証し、結果を7日保存する。速度に恣意的な合格線は設けない。

[測定結果](benchmarks/2026-10-06-local.json)はローカルの比較用で、本番CloudflareのD1遅延・同時利用者数・混合負荷の容量を示さない。書き込みQueueの実処理、Push配信、バックアップ、大きい画像、広域ネットワークはこの測定の対象外。

最終測定は5千・2万・5万投稿、各経路120回・並列12で、合計2,520応答すべてHTTP 200、検証エラー0件。下表はp95ミリ秒。型検査・単体/E2E検査の終了後に測定した。

| 経路                        | 5千投稿 | 2万投稿 | 5万投稿 |
| --------------------------- | ------: | ------: | ------: |
| 公開一覧（KV / キャッシュ） |   16.28 |   35.36 |   26.27 |
| 文字検索                    |   26.96 |   54.26 |   97.49 |
| タグ                        |    32.1 |    52.9 |  101.04 |
| 近傍                        |   31.99 |   68.58 |  143.55 |
| 深いページ                  |   49.69 |  145.07 |  320.93 |

深いページはOFFSET 4,900 / 19,900 / 49,900。公開一覧と比べ、文字・タグ・近傍・深いページは件数による時間増加が見える。この比較を次のSQL改善候補の根拠にし、本番の処理能力へ換算しない。

## 次に実施する順序

1. **隔離したCloudflare環境で混合負荷を測る**。公開キャッシュが温かい場合と冷えた場合、検索・近傍検索、オフラインからの集中再送を組み合わせる。段階的に負荷を上げ、APIのp95/p99、5xx、D1行読み・SQL時間、Queue最古待ち時間、受付から反映まで、DLQを記録する。本番へ合成書き込みを送る試験はしない。想定人数・目標の反映時間が決まったら合否条件にする。
2. **重い読み取りを測定結果から改善**。タグは`post_tags`の索引、文字検索は全文検索、深いOFFSETはカーソル方式、近傍検索は範囲での候補削減を検討する。意味や表示順を保って比較する。読み取りがprimaryを圧迫する場合は[D1 read replicationとSessions API](https://developers.cloudflare.com/d1/best-practices/read-replication/)を検討する。有効化だけでは既存APIが自動でreplicaへ移らない。権限確認や書き込み直後の読み取りの整合性を先に設計する。
3. **入力制御と運用監視を広域化**。現在のrate limitはisolate内のメモリで、分散アクセスを通じた総量制限ではない。端末記録の作成やQueue投入前の制御、WAFやRate Limiting bindingなどを検討し、避難所の共有回線をまとめて拒否しないようにする。Queue受付失敗時には同期書き込みへ戻る既存経路もあり、過負荷時のDB保護策は残課題。独立した外部ヘルス監視とQueue滞留・DLQの通知も未追加。
4. **増量前にバックアップと復元を実測**。下記の200ページ上限、コピー時間、一時コピー込みのD1容量、復元時間を確認する。APIが5万投稿を読めても、その件数を現行の日次バックアップで保存できる証明にはならない。外部エクスポートと保管方式の拡張を先に用意する。
5. **必要になった段階でDB分割・移行を判断**。地域別の運用境界、DB容量、持続的な書き込み遅延などを根拠にする。投稿数や「複数自治体」という名前だけでPostgreSQL移行を決めない。画像のR2直接配信も利用量とアクセス制御を確認して判断する。

## 日常の確認と障害対応

Workersのリクエスト数・CPU・4xx/5xx、D1のrows read/written・SQL時間・overload、両Queueの最古待ち時間・backlog・DLQ、KV鮮度と実使用量、R2容量・操作数・バックアップ取得時刻を見る。10%ログは全イベントの記録ではない。必要な事象は管理画面の記録とCloudflareの指標でも確認する。

初期の運営目安は「5xxが5分続く」「書込Queueが5分以上滞留」「DLQが1件以上」「最終バックアップ取得から26時間以上」。容量の限界やサービス保証値ではない。負荷と現地運用の結果で調整する。

過負荷時はまずKV鮮度・Queue・D1を確認し、重い一括インポートや連携取得を止める。公開キャッシュの延長は情報の古さが増えるため運営判断とセットにする。状況更新を無言で捨てる間引きは行わない。受付停止が必要な場合は利用者へ示し、既存の未送信データを保持する。[運用手順](OPERATIONS.md)に沿って時刻・影響・対応を記録する。

### バックアップの規模と上限

17対象表を一つのD1 batchで一時テーブルへコピーし、不変のコピーをページ読み出ししてR2へmultipart保存する。JSON全体はメモリに保持しない。ページは最大128行、元データ256KiBを目安とし、一行だけで超える場合は2,000,000バイトまで扱う。JSONのエスケープと列名で実際の使用量は増える。送信バッファは5MiBで、全表合計200の非空ページを安全上限とする。超過時は不完全なアーカイブを成功として扱わず、既存の保存世代を残す。

[D1の上限](https://developers.cloudflare.com/d1/platform/limits/)はPaidでDB 10GB、1実行1,000クエリ、一つのbatchは30秒。コピーの分だけDB使用量が一時的に増え、規模により書き込み待ちも発生する。コピー所要時間とD1使用量を実測する。[Workersの上限](https://developers.cloudflare.com/workers/platform/limits/)はメモリ128MB、Paidのサブリクエストは既定10,000。分割送信だけでコピー時間やDB容量の上限がなくなるわけではない。

手動・定期は20分期限の更新可能なリースで直列化する。強制終了の残骸削除と旧世代整理は各100件/実行までで、残りは後続実行へ持ち越す。容量に余裕がない場合、コピーが30秒に近づく場合、安全ページ数を超える場合は、非公開端末での `wrangler d1 export` を先に確保し、外部ジョブによる保管やDB分割を検討する。最新データの取得開始時刻、保存容量、全処理時間、復元所要時間を記録して判断する。
