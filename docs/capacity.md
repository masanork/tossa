# tossa.app の捌ける規模と、溢れたときの手順

現行は Cloudflare Workers Paid + D1 1本 + R2 + Queues。読み取りはエッジキャッシュ、書き込みは Queue でならす前提。数字は 2026-09 の [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) と実装に基づく目安で、保証値ではない。

## いまの構成で見てよい規模

| | 目安 | 根拠 |
|---|---|---|
| 投稿件数 | 1,000〜5,000（局所的な災害想定） | 一覧は 50 件ページ、タグ `json_each` もこの件数なら実用 |
| 同時閲覧 | 数千〜1万。キャッシュが効けば数万 | 公開一覧は Cookie を無視して 15 秒キャッシュ |
| 1日の閲覧 | 10万〜数十万 PV | 静的 JS/CSS は Worker を通さない。API はキャッシュヒットが本体 |
| 書き込み | ピークで毎分 100〜数百件の投稿・状況更新 | D1 は単スレッド。Queue がバーストを吸収 |
| 同時書き込み | 秒間 10〜20 を超えると遅延・overload | 1クエリ 5〜20ms なら理論上は秒数十だが、実効はそれ以下 |

局所的な災害時の実績（登録約 4,000、1日約 7万、最大同時約 3,000）は、**1自治体・生活情報板**として現行で収まる想定。都道府県全域の「全避難所を常時ピン」や、全国1インスタンスは想定外。

Workers Free の D1（読み 500万行/日で打ち止め）では災害ピークに耐えない。現行は Paid 前提。

## 先に潰すボトルネック（コード側）

実装済み:

1. **公開 `GET /api/posts` を Cookie 非依存で 15 秒キャッシュ**
2. **一覧 SQL から `image_meta` を外す**
3. **Wrangler 4 + `run_worker_first = ["/api/*", "/posts/*", ...]`** — JS/CSS は Worker を通さない
4. **KV `FEED_KV` に公開フィードのスナップショット** — フィルタなし一覧は D1 を踏まない（Workers Paid の KV 枠内）
5. **サイトマップ / llms-full を 200 件、フェデレーション GeoJSON を 2,000 件で打ち止め**
6. **アクセスログ 7 日保持**（日次 cron）
7. **管理画面「規模」タブ** — 投稿数・書き込み・スナップショット鮮度と、その数字に基づく推奨

まだコードではやっていない（次の段）:

- タグ用 `post_tags(tag, post_id)` 交差テーブル（投稿が 1 万を超えて語彙フィルターが遅いとき）
- R2 バケットをカスタムドメインで直接配信（`/api/images` の Worker 経由をやめる）
- 自治体ごとの D1 分割、または Hyperdrive + PostgreSQL（**課金が増える**ので、規模タブが「act」を出したとき）

## ボトルネックの現れ方

| 症状 | だいたいの原因 | まずやること |
|---|---|---|
| 一覧が数秒〜タイムアウト、D1 `overloaded` | 単スレッド D1 に読みが集中。キャッシュミス | キャッシュ TTL を 15→30 秒。ダッシュボードの D1 行読みを確認 |
| 投稿・バッジ更新が失敗、Queue 滞留 | 書き込みバースト | 状況更新をさらに間引く。書き込み Queue の lag を見る |
| 無料枠エラー（行読み超過） | Workers Free のまま | **即 Paid**。災害当日に Free は使わない |
| 画像付き投稿が 2MB エラー | Data URL が D1 行に残っている | R2 必須。古い行の `image_url` を掃除する |
| タグ絞りが遅い | `json_each` 全件 | `post_tags` を足す |
| 地図が重い | クライアントが全件ピン | 表示中 bbox だけ取る API（未実装） |

## 溢れたときにやること（手順）

災害が「1自治体の生活情報板」を超えたら、この順。

### 1. 当日（設定だけ）

1. Cloudflare ダッシュボードで Workers / D1 が Paid であること
2. 公開一覧の TTL を一時的に 30〜60 秒に延ばす（コードの `s-maxage=15`）
3. 不要な SEO エンドポイント（`/llms-full.txt`）を WAF か Worker で短時間 503
4. 管理画面の一括インポート・フェデレーション取り込みを止める（読み書きの大食い）

### 2. 件数 1 万、同時 1 万を超えたら（小さな改修）

1. 公開フィードを **KV スナップショット**にする。Queue 消費後に `posts:public` JSON を KV へ書き、GET は KV だけ見る
2. タグを交差テーブルにする
3. 画像を `tossa-images.tossa.app` のような R2 カスタムドメインへ
4. `access_logs` を 7 日で削除する cron

KV スナップショットが効くと、閲覧は D1 をほぼ踏まない。書き込みだけ D1。

### 3. 都道府県・複数自治体（設計の切り替え）

1インスタンスの D1 10GB・単スレッドは、全国の避難所マスタ＋状況更新には向かない。

- **自治体（または二次医療圏）ごとに Worker + D1**。いまのフェデレーション GeoJSON で隣同士を同期
- または **読み専用レプリカ / 別 D1** に一覧を置き、書き込み D1 と分ける
- 地図はタイルと bbox クエリ。全件 GeoJSON は配らない

この段に来たら「tossa.app が日本の全部」ではなく「tossa.app は製品サイト、実データは `tossa.example.lg.jp`」が正しい。

## 監視

ダッシュボードで日常的に見るもの:

- D1: rows read / written、overload エラー
- Workers: リクエスト数、CPU、4xx/5xx
- Queue: `tossa-write-queue` と `tossa-push-queue` の backlog
- R2: クラス A/B オペレーション

閾値の目安: D1 書き込みが持続的に秒間 10 を超える、Queue lag が数分、5xx が閲覧の 1% を超える、のいずれかで「段階 1」に入る。
